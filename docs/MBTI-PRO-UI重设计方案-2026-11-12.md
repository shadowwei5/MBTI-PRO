# MBTI-PRO UI 重设计方案（审核稿）

> 日期：2026-11-12  
> 范围：首页、答题页、结果页已完成方向稿；分享海报与旧组件仍待统一。  
> 目标：去掉“AI 生成模板感”，建立更像独立心理测评品牌、而非通用 SaaS 落地页的视觉语言。

---

## 一、当前页面为什么显得“AI 味重”

不是单一颜色或字体的问题，而是几个模板特征叠加：

| 问题 | 当前表现 | 造成的观感 |
|---|---|---|
| 动态渐变背景 | 米色渐变 + 20 秒循环漂移 | 像套用 AI 生成模板 |
| 发光/流光文字 | 标题使用 shimmer 渐变字 | 视觉廉价，且与“心理测评”的克制感冲突 |
| 大量圆角卡片 | 4 个信息卡、表格、结果卡、兑换卡 | 像通用 SaaS / 小红书模板 |
| 居中大标题 | “发现真实的自己”居中 + 两行 | 缺少编辑设计感，像套模板 |
| 81 张图片墙 | 首页加载 81 张人格插画和说明 | 首屏之后极长，移动端高度 19,450px |
| 字体系统不统一 | Playfair + Noto Sans + 装饰字 | 中文标题没有独立气质，像英文模板套中文 |
| 信息密度失衡 | 大量“是什么/为什么/优势”说明 | 像产品说明书，不像一次自我探索的入口 |
| 没有“品牌签名” | 每个区块都是通用卡片 | 用户记不住页面，只记得“米色 + 圆角” |

**核心判断：** 不是把圆角改小、颜色改深就能解决；需要换一套**编辑型视觉系统**，让页面像一本心理档案/杂志，而不是一个 AI 生成的落地页。

## 二、调研结论

### 2.1 同类产品

| 参考 | 做得好的地方 | 不照搬的地方 |
|---|---|---|
| 16Personalities | 单一强 CTA、明确“10 分钟”、一句强主张、插画承担情绪 | 插画成本高，且容易变成“卡通人格” |
| Truity | 衬线大标题 + 深绿品牌带 + 研究/媒体背书，专业感强 | 信息密度高，首页仍偏“测评超市” |
| 韩国色彩人格测试 | 极简、单题单屏、强分享 | 过于娱乐化，不适合 81 型深度定位 |
| 日本人格/旅行人格项目 | 手绘、纸张、编辑排版、低饱和红 | 插画依赖强，不适合当前“零图片”性能目标 |

### 2.2 编辑型设计原则

调研到的有效原则，和当前页面几乎相反：

- **暖白/纸色画布**，不要纯白，也不要用动态渐变；
- **近黑墨色**作为主文字，不要用彩色渐变字；
- **一个强调色**，只用于关键动作/数字/印章，不要每个区块换色；
- **超大号、常规字重的衬线标题**，用字号建立层级，不靠粗体和阴影；
- **1px 细线**组织版面，不用大量圆角卡片；
- **不对称布局**：左文右图/右坐标，不要所有内容居中；
- **有限圆角**（0-4px），不要 20-24px 大圆角；
- **动效只做 hover 和入场**，不做持续呼吸、漂移、发光；
- **删掉不必要的装饰**：光晕、漂浮圆点、渐变、玻璃拟态。

参考：
- 16Personalities 首页的单一 CTA 与强主张；
- Truity 的衬线标题、深色品牌带、信任信息；
- Refero / editorial minimal 的纸张底色、细线、超大字号、无阴影系统；
- 日本人格平台的“简约、留白、克制”原则。

## 三、三个方向与推荐

### 方向 A：纸上心理档案（推荐，已做首页方向稿）

**关键词：** 纸张、档案、编辑部、朱砂、墨色、细线、编号。

- 底色：暖纸色 `#F2EDE3`
- 主文字：墨黑 `#1E1D1A`
- 强调：朱砂 `#A63D2C`
- 深色带：墨绿 `#2F4037`
- 标题：Noto Serif SC / 宋体，超大字、常规字重
- 正文：Noto Sans SC，16px / 1.95
- 标签：DM Mono，小号大写字距
- 图形：四维坐标线，不用图片

**为什么推荐：**
- 最贴合“人格档案/自我探索”的内容属性；
- 与 16Personalities 的卡通插画、Truity 的测评超市形成差异；
- 不需要 81 张图，天然解决首页加载；
- 可自然延伸到测试页、结果页、分享海报；
- 对小红书女性用户不冷、不硬，但也不“可爱廉价”。

### 方向 B：夜间研究所

**关键词：** 深绿、奶油字、实验档案、夜间。

- 深墨绿/近黑背景，奶油色文字，朱砂或铜色强调；
- 更像高端心理研究所/会员制报告；
- 风险：首页偏重，小红书内置浏览器下长文阅读容易疲劳；分享海报也偏暗。

### 方向 C：瑞士数据网格

**关键词：** 纯白、黑、红、网格、编号、数据。

- 白底黑字，红色只做标记；
- 更像设计工作室/数据产品；
- 风险：太冷，和目标用户的“被理解”情绪有距离。

**推荐：A。** 保留纸张的温度，同时用编辑排版去掉模板感；深色只放在底部 CTA 带，形成节奏。

**分享海报重排**

之前的问题是类型码 150px 大字横向撞到右上角的人格图框（图片框 x=500 起，ESTJ 实际宽度约 347px，从 x=80 起算到 427，几乎贴住框线），加上画布没有等待字体加载，回退字体会让文字进一步右溢。

本次做法：

| 项 | 之前 | 现在 |
|---|---|---|
| 画布 | 800×1200 | 800×1340 |
| 人格图 | 215×285（挤在右上角） | **340×340**（x=390..730，独立方块） |
| 类型码 | 150px，与图片框同水平带 | 150px **通栏自适应**，永远在图片下方 |
| 组名 | 出现两次 | 只保留左上角一处 |
| 坐标线右端字母 | 右对齐在 720，离线尾 160px（断裂） | 紧贴线尾 x2+16 |

```ts

// 类型码自适应缩放，任何 4 字母组合都不会越界
function fitFontSize(ctx, text, fontTemplate, maxWidth, startSize) { ... }
```

### 4.6 字体本地化与局域网调试（2026-11-12 下午）

**字体本地化**

原来 `index.html` 从 Google Fonts 加载 `Noto Serif SC / Noto Sans SC / Playfair Display / DM Mono`。国内基本不可达，手机端会整页退化成系统字体，分享海报的 canvas 排版也会错位。

改法：

- 只自托管**拉丁字符子集**（中文系统字体足够好，且体积巨大不划算）：
  - `client/public/fonts/playfair-600-latin.woff2`（38KB）
  - `client/public/fonts/playfair-700-latin.woff2`（38KB）
  - `client/public/fonts/dmmono-400-latin.woff2`（15KB）
  - `client/public/fonts/dmmono-500-latin.woff2`（15KB）
  - 合计约 **107KB**
- 中文一律走系统字体栈：
  - 衬线：`Songti SC / STSong / SimSun / Noto Serif CJK SC / Source Han Serif SC`
  - 无衬线：`PingFang SC / HarmonyOS Sans SC / Microsoft YaHei / Noto Sans CJK SC`
  - 等宽：`DM Mono / SF Mono / Consolas / Roboto Mono`
- `index.html` 删除 Google Fonts `<link>`，改为 preload 两个 woff2；
- 海报 canvas 显式 `document.fonts.load()` 后再 `document.fonts.ready`，确保画布用的是本地字体而不是回退字体。

验证：Playwright 拦截 `googleapis.com` / `gstatic.com` 全部 abort（模拟国内网络），外部字体请求 **0 个**，Playfair 与 DM Mono 均本地加载成功，结果页与海报排版完全正常。

> 坑：批量替换字体栈时如果把整串字体列表包进一对引号（`"DM Mono, SF Mono, ..."`），CSS 和 canvas 都会把它当成**单个字体名**而彻底失效。必须逐个字体名加引号。

**局域网调试**

- 本机地址 `192.168.1.2`（Realtek 有线），网关 `192.168.1.1`；手机连同一路由器 WiFi 即可访问 `http://192.168.1.2:3001/`。
- 服务端 `app.listen(PORT)` 默认监听 `0.0.0.0`；Windows 防火墙三个配置文件均为 Disabled，且已有 Node.js 入站放行规则，无需额外配置。
- 路由上 `192.168.1.0/24` 走以太网，不会被 `YuShe-TUN`（Meta Tunnel）劫持。
- CORS 白名单已加入 `http://192.168.1.2:3001 / :5173 / :4173`，并支持 `EXTRA_ORIGINS` 追加。
- 本机测试局域网地址时必须绕过代理（`curl --noproxy '*'`），否则会命中 `http_proxy=127.0.0.1:13976` 报 502。

### 4.7 第五轮：ABCD 归因修复 + 选项语义化（2026-11-12 下午）

**问题一：手机端每次结果都是 ABCD**

现场证据（`TestRecord` 表，用户手机 `Linux armv81 / 359x803`）：

```
type=ABCD  ansCount=40  dist={C:2, B:3, E:29, A:2, D:4}
dimAnswered={10,10,10,10}   dimTotals={25,25,25,25}   duration=117s
```

40 题**全部作答了**，其中 29 题选了 E（非常右），结果却是 ABCD。

根因链：

1. `TestView` 把整份题目列表写进 `localStorage['mbti-pro-test']`；
2. 题库从 100 题改成 40 题后，**旧缓存仍在**，恢复时直接用 `parsed.questions` 覆盖 API 结果并 `return`，完全不再请求 API；
3. 于是 `questions.length` 变成 100（每维 25），`dimTotals` = 25/25/25/25；
4. 后端 `thresholdFor(25)` = **±17**，而实际只答了 10 题/维（最大 ±20）→ 29 个 E 也只得到约 −14~−16，**小于阈值 → 落进中间档 → ABCD**。

修复（三层）：

| 层 | 改动 | 文件 |
|---|---|---|
| 数据源 | 题目列表永远以 API 为准；缓存只在**题目 id 序列完全一致**时恢复，否则丢弃 | `client/src/views/TestView.vue` |
| 存储 | 存档只写 `questionIds` 指纹 + 答案，不再塞整份题库 | 同上 |
| 计分 | 阈值改为按**实际计分题数** `dimScored` 计算，而不是题目总数 | `server/src/services/scoring.ts` |
| 上报 | 提交时只上报真正作答过的题 id | `client/src/views/TestView.vue` |
| 兜底 | 一题未答时阻止提交并给出提示 | 同上 |

回归用例见 `server/src/services/__tests__/scoring.test.ts` 的「题库残留导致的 ABCD 回归」组（4 个用例）。

修复前后对比（同样 38×E + 2×D）：

- 修复前：`ABCD`，dimTotals 25/25/25/25
- 修复后：`INFP`（内向型·直觉型·情感型·感知型），dimTotals 10/10/10/10，置信度 63%

**问题二：手机端「左 / 右」有歧义**

手机端两段陈述是上下排列的，但选项文案写的是「非常左 / 偏左 / 偏右 / 非常右」，指向错误的一段。

题库约定已核实：每道题的 `textLeft` 固定对应左侧端，`textRight` 固定对应右侧端：

| 维度 | 左端 | 右端 |
|---|---|---|
| E_I | E 外向 | I 内向 |
| S_N | S 实感 | N 直觉 |
| T_F | T 思考 | F 情感 |
| P_J | J 判断 | P 感知 |

改法：**选项文案改用维度语义词，完全不依赖位置**，桌面端和手机端都不会歧义。

- 端点标签：`E · 外向` / `I · 内向`（原来是「左侧陈述 / LEFT」「右侧陈述 / RIGHT」）
- 五档选项：`非常外向 / 偏外向 / 两者之间 / 偏内向 / 非常内向`（其余维度同理）
- 题干 meta 行增加轴向提示：`外向 E ↔ 内向 I`

改动文件：`client/src/components/OptionGroupBipolar.vue`、`client/src/views/TestView.vue`

截图：`docs/ui-audit/final-test-mobile.png`、`docs/ui-audit/final-test-desktop.png`

### 4.8 第六轮：选项去字母 + 中性化（2026-11-12 下午）

用户反馈：上一版把选项改成「非常外向 / 偏外向 / …」虽然消除了左右歧义，但**直接把测量维度写在答案里，带有明确的倾向暗示**——用户会按"我自认为是外向的人"作答，而不是按真实行为作答（社会期许偏差）。

改法：改用**不暴露维度、不依赖空间位置的角色标签**。

| 位置 | 上一版 | 现在 |
|---|---|---|
| 端点标签 | `E · 外向` / `I · 内向` | **正方** / **反方** |
| 五档选项 | 非常外向 / 偏外向 / 两者之间 / 偏内向 / 非常内向 | **非常认同正方 / 比较认同正方 / 中立 / 比较认同反方 / 非常支持反方** |
| 题干 meta | 能量来源 · `外向 E ↔ 内向 I` | 仅保留 `能量来源`（去掉轴向提示） |
| 选项字母 | 显示 A / B / C / D / E | **不显示**，key 仍为 A~E 仅供计分 |
| 选项下方提示 | 「按你平时的真实状态作答…」 | 删除（与副标题重复，且手机端被固定底栏遮挡） |

这套标签同时满足三个约束：

1. **不暴露测量意图** —— 用户看不到外向/内向等维度词；
2. **不依赖空间位置** —— "正方 / 反方" 是逻辑角色，桌面端左右排列、手机端上下排列都不歧义；
3. **不显示字母** —— 避免 A~E 产生"评分等级"的暗示。

实现要点：

- 手机端每格约 68px，六字文案一行放不下 → 拆成两行（主述 `非常认同` + 阵营 `正方`），桌面端仍一行显示；
- `OptionGroup.vue`（客观题组件）里的 `option-key` 字母也一并去掉；
- `scoring.ts` 与题库完全不用改 —— emit 的 key 仍是 A~E。

验证：全选第 1 档提交，`answers` 为 40 个 `A`，结果 `ESTJ`，计分链路未受影响；手机/桌面均无横向溢出、无 JS 错误。

截图：`docs/ui-audit/neutral-final-mobile.png`、`docs/ui-audit/neutral-final-desktop.png`
